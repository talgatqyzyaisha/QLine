# QLine product and domain contract
Source: user brief, 15 October 2026. Stack: vanilla HTML5/CSS3/ES modules; Node.js Express; Supabase PostgreSQL/Auth. No payments or medical records.
## Runtime and release
Production runtime uses only Supabase. No test-persona endpoint and no browser-local booking store exist. Public content comes from the API; lack of data is not replaced with fictional clinics. Account creation requires reviewed release configuration and database-recorded consent. Email/password registration, confirmation and recovery use real Supabase Auth endpoints; SMS is available only for existing verified numbers after provider configuration. Test fixtures are excluded from deployment.
## Identity and authorization
Supabase user identity, never client-supplied user IDs. Patient reads own visits. Membership owner/admin manages clinic; dentist reads assigned visits and marks completed/no_show only. Platform admin is granted exclusively by database operator. Privileged database functions enforce roles. Browser never receives secret/service-role keys. No selectable administrative test persona exists in runtime.
## Booking lifecycle
pending → confirmed/cancelled; confirmed → cancelled/completed/no_show. Patients cancel future pending/confirmed bookings and request reschedule; request does not release or move an appointment. Clinic can atomically move a pending/confirmed visit to a free same-service slot, then resets reschedule request. Pending is never labelled confirmed. All status changes and important admin/clinic mutations are audited.
## Availability and concurrency
Explicit open slots generated by clinic from working-hour templates, minus blocked intervals. Every slot has a dentist, service, start/end. PostgreSQL exclusion constraint prevents overlapping active visits per dentist; appointment transaction locks slot, rechecks clinic approval, time and availability. Reusing idempotency key with different data is rejected. Idempotency is scoped per patient.
## Legal, privacy and retention
Unapproved legal/contact placeholders have no legal effect. Production launch blocked until policies, consent and cancellation rules are approved by operator/legal reviewer. No diagnoses requested. Test fixtures must be synthetic and never seeded into the live project. Production export/retention/deletion processes and jurisdictional hosting require organizational decisions; no unverified compliance claim. No analytics trackers installed. Payments out of scope.
