# Состояние подключения и выката

## Подготовлено
- Runtime использует только Express + Supabase. Выбор фиктивной роли, статический demo API и localStorage записей удалены.
- URL и переданный publishable key записаны в локальный игнорируемый Backend/.env; секрет сессии создан локально.
- Регистрация email/password, подтверждение, вход, logout, refresh, recovery и новый пароль реализованы в исходниках.
- Миграции Supabase, consent trigger, RLS/конкурентная запись, Dockerfile, Railway config и GitHub CI подготовлены.
- Целевой GitHub: https://github.com/talgatqyzyaisha/QLine.

## Проверенные препятствия
- Read-only GET Supabase `/auth/v1/settings` из этой среды: HTTP 403. Действительность ключа и настройки проекта не подтверждены.
- `git ls-remote https://github.com/talgatqyzyaisha/QLine.git HEAD`: HTTP 403, "Calls to this URL are not allowed". Содержимое репозитория неизвестно.
- npm registry: HTTP 403, Express-зависимости не установлены. Lockfile не придуман.
- GitHub ещё не подключён к чату. Наличие URL репозитория не создаёт авторизованную сессию.
- Приложения Supabase и Railway помечены DISABLED_BY_ADMIN в рабочем пространстве. Для их использования здесь нужно разрешение администратора рабочего пространства.
- PostgreSQL URL содержит `[YOUR-PASSWORD]`, а не действующий пароль; Supabase CLI session отсутствует.
- Юридические JSON и версия согласия пока не утверждены: регистрация и запись не открываются автоматически.

## Что фактически не выполнено
Ни одна миграция не применена к указанному Supabase из этой сессии. Файлы не загружены в GitHub. Railway-сервис/домен не созданы, deployment не запускался. Ранее опубликованный статический адрес QLine остаётся предыдущей версией до замены настоящим Node-сервисом.

## Для продолжения
1. Подключить GitHub в этом чате с доступом к конкретному репозиторию.
2. Разрешить Supabase/Railway подключения в настройках рабочего пространства и авторизовать нужные проекты либо использовать разрешённую рабочую среду с этими сервисами.
3. Передать необходимые секреты через защищённые настройки окружения/сервисов, а не в исходники или открытый чат.
4. Проверить реальную схему, применить migrations dry-run/push, настроить SMTP/redirects и утвердить release configuration.
5. После CI создать Railway deployment и проверить настоящий end-to-end сценарий. Только после успешной проверки считать проект запущенным.
